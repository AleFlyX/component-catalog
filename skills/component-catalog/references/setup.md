# First-time enrollment

Use this workflow when the user requests setup or expands the selected catalog scope. Adapt to existing project conventions; do not ask the user to hand-author the configuration or JSDoc that the Agent can derive.

## Inspect and choose scope

Locate the installed skill directory from this SKILL.md, or use an existing compatible project CLI. The skill includes scripts/bin/component-catalog.mjs, scripts/lib, scripts/schema and scripts/package.json/package-lock.json. A copy of only Markdown is incomplete; obtain the entire skills/component-catalog directory from the selected repository revision. Do not guess a registry package or repeatedly retry a missing command. Use command-specific --help when syntax is unclear; init only prints a template. If a project script always injects --config, call the bare CLI for scan/init and doctor --installation, which do not use project configuration.

### Install and diagnose

Use Node >=22. For a skill-only installation, invoke `node <skill-directory>/scripts/bin/component-catalog.mjs doctor --installation --expect-version 0.3.0`. If TypeScript is missing and setup is authorized, run `npm ci --prefix <skill-directory>/scripts --ignore-scripts --no-audit --no-fund` and retry doctor. Resolve and quote the actual path; do not run this install in the consumer project's package root. Registry access or an existing npm cache is needed; a failed install is a prerequisite failure, not an empty component inventory. Do not copy node_modules from another machine or commit installed dependencies. A local read-only skill directory needs a writable installation location; report that constraint rather than silently falling back to consumer dependencies.

Default to one active installation: the self-contained skill. Do not also clone a full tool repository into the consumer's .agents/tools or similar directory. The source is https://github.com/AleFlyX/component-catalog.git; no registry package is published. A separate checkout is only needed for tool development or an explicitly chosen installation, and belongs outside the consumer workspace. For existing duplicates, inspect command references and local changes, report which installation is active, and leave unused copies intact unless cleanup is authorized. Do not invent release tags or silently update an existing checkout.

The bundled tool may run by absolute path without a consumer dependency. Alternatively run npm pack in the full tool checkout with a destination outside the consumer repository, then install that explicit local tarball as a dev dependency using the consumer's existing package manager. Copy the entire skills/component-catalog directory from the same version into the Agent's supported skill location; exclude any locally installed node_modules. The repository's test directory is for maintainers and is outside the installable skill and npm package; it need not be copied or deleted during setup. Keep temporary archives and validation materials outside the consumer repository; package scripts, lockfile and intentional skill/config integration are normal setup artifacts.

Run `doctor --installation --expect-version 0.3.0 --expect-skill-revision 10` with the active bundled CLI. It checks Node, CLI version, bundled instructions revision and TypeScript. Revision is independent of CLI/schema versions; an older 0.3.0 installation may lack this option. An unknown option means inspect and align the complete installation, not retry without the check and claim alignment. Doctor inspects its own SKILL.md, so use the entry belonging to the instructions loaded by the Agent. It does not discover every copy or verify document content cryptographically. Missing dependencies require restoring the corresponding installation; doctor never installs anything.

If an older CLI reports doctor or --version as unknown, inspect that installation's package.json and align it with the intended skill version; do not repeatedly retry unsupported commands.

After configuring, run `doctor --config <config-path> --expect-version 0.3.0`. Findings return stdout JSON and exit 1; invalid invocation returns stderr and exit 2. A missing catalog is not_run, so a first-time project can be ready before enrollment. pass only means readiness; continue with audit, generate and check. On CLI/skill mismatch, update both to the intended pinned version within setup scope, or report the unavailable version; do not change the expected version to bypass the check. Project diagnosis checks tsconfig and static module/type dependency resolution, not all type errors, runtime behavior or whether package scripts actually invoke check.

## Read-only inventory

Inspect package scripts, application tsconfig/jsconfig/extends, existing aliases, component ownership rules and example conventions. Run scan against the user-provided frontend directory before changing sources. The scanner needs no frontend dependencies or markers. It considers exported PascalCase functions/value declarations and some unsupported export forms; classes, wrappers and reexports may appear as unsupported. Ordinary functions/constants can be false positives. Plain .js/.jsx/.ts/.tsx are scanned; .d.ts, node_modules, .git and descendant symlinks are skipped. Other source formats need source inspection, not a claim of zero components.

```bash
component-catalog scan <frontend-directory> --summary
component-catalog scan <selected-directory> --limit 20
component-catalog scan <selected-directory> --offset <nextOffset> --limit 20
```

Follow nextOffset until null in the same directory/view before reporting full coverage, or explicitly report a partial inventory.

For targeted discovery, use `scan <directory> --query <name-or-path-terms>` instead of `--summary`. This filters names, paths, summaries and task tags without requiring markers or configuration. It can surface unsupported or undocumented candidates; those still need source review before enrollment. Filtered pagination is not a complete inventory of the selected scope: counts cover the whole directory, matchingCandidates covers the query. For discovery fallbacks, see [the skill workflow](../SKILL.md#discover-beyond-the-catalog).

Use paths, real import sites and project architecture to recommend public component directories. Begin with scan --summary on a broad frontend tree; its immediate-child groups include descendants, and '.' represents root-level files. Drill into likely public directories before requesting detail pages. Do not read all frontend candidates merely to count directories. Do not recommend all pages, feature-private widgets or test/preview exports merely because scan lists them. Present a small table: directory, candidate count, existing markers, unsupported count and reason for recommending/excluding it. Counts must describe the reviewed scope; pagination or unread sources mean partial evidence. Scan has no config-based filtering, so inspect only relevant directories for a focused inventory and resolve its sourcePath against its returned root. Keep the same view and directory across nextOffset pages; restart pagination after source edits.

## Scope decisions

If the user already explicitly selected enrollment scope, continue. Otherwise ask one concrete choice after discovery. A frontend path identifies where to inspect, not which exports to enroll. Include real paths/counts rather than generic questions. Existing setup authorization covers ordinary configuration/annotation edits in that chosen scope. Do not add an extra approval step for each batch or component. Inventory-only requests end with findings and no writes.

Prefer the client's eligible structured question tool, asynchronous when available; follow its actual schema and mode rules. Ask two or three concrete options with the recommended choice first and brief consequences. Do not switch modes merely to obtain a question UI. If no eligible tool exists, use one concise numbered text question and explain that this client/mode cannot show the choice UI.

While an asynchronous choice is pending, continue independent read-only work such as aliases, real consumers or installation readiness. Wait for an actual answer before dependent writes; a preselected option, dismissal, empty response or timeout is not consent. If independent work is exhausted, keep the decision pending using the client's mechanism. A text-only fallback may require yielding; do not promise non-blocking interaction on every client.

For an inspected mixed src/components tree containing UI and auth/chat/home business components, a suitable question is “Which component coverage should this catalog use?” with options adapted to the actual evidence:

- “Shared UI + reusable business components (recommended)” — enroll reviewed reusable entries, preserving module boundaries; exclude page-private widgets.
- “Shared UI only” — enroll the identified common UI directory/subset and leave business components outside this setup.
- “Inventory only for now” — report the candidates without configuration or annotation changes.

Recommend the first option only when the inspected project supports it; otherwise recommend the narrower justified scope. Let the client accept a custom scope where supported. Do not offer “make all src/components public” merely because the folder contains components. Mixed ownership can use enrollment: review; project-wide reuse still requires architectural evidence. After sending an asynchronous question, continue checking aliases, existing uses or installation readiness without making scope-dependent edits. This is a pending scope choice, not a tool failure or a reason to abandon all work.

## Configure from the project

Preserve existing config and package scripts; edit only what is needed. Use configVersion 2:

Choose the compiler config that owns the selected application source. A solution-style root with `files: []` and project references does not inherit aliases or JSX settings from its children; point `tsconfig` to the relevant app config, such as `tsconfig.app.json`. The CLI diagnoses this explicitly rather than guessing among applications. Composite analysis retains the configured source program's file membership, so its diagnostics can include files beyond the selected components; resolve/report them without disabling composite or narrowing roots to hide errors.

- projectRoot is relative to the config file; sourceRoot, tsconfig, catalog and array paths are relative to projectRoot. sourceRoot is one source tree, with separate configs for independent applications.
- componentRoots are disjoint reviewed scopes with path, stable idPrefix, importPrefix, layer and enrollment. Set enrollment to public for an already agreed public component scope, or review for mixed ownership where each candidate needs a reasoned decision. Do not infer public policy from a folder name alone. Each path is within sourceRoot. Use an existing real alias/package subpath as importPrefix (no trailing slash), or explicit null when the project uses relative imports; init defaults to null. IDs are derived from root-relative directories and export names; `importPathStyle: "barrel"` only changes the suggested importPath, never IDs or ownership. Do not invent runtime aliases or move components to satisfy the tool.
- importExtension optionally selects omit (default), js (compiler output suffix: .js, or .jsx for JSX/TSX with jsx: preserve), or preserve (source extension retained). Follow actual consumer imports and compiler/runtime conventions: NodeNext ESM commonly needs js; preserved TS suffixes require allowImportingTsExtensions or relative imports with rewriteRelativeImportExtensions. Generation resolves suggested paths using the recorded examples' import conditions and verifies the same public component export, including forwarding entrypoints. This does not validate arbitrary callers, package build output or runtime loaders; run project checks on actual integration.
- catalog is a dedicated .json output, preferably outside sourceRoot. Never point it at a source/configuration file. Explicit generate overwrites this output; --check is read-only.
- exclude, previewRoots and testRoots use project-relative paths inside sourceRoot, not globs. Outputs outside sourceRoot need no exclusion. previewRoots/testRoots cannot overlap.
- vocabulary maps the user's ordinary terms to actual primary/related task tags. The Agent completes it for the enrolled categories, rather than retaining only init's button example. For a Chinese project, input controls might need 输入框→input, drawers 抽屉→sheet, errors 错误提示→error-feedback; use these only when those task tags actually exist. Preserve existing mappings. No built-in taxonomy or arbitrary natural-language understanding is assumed. For mixed Chinese/English queries, include both forms for each role; e.g. 顶部导航栏/navigation bar/navbar→ui-nav-bar, 状态标签/status tag→ui-status-tag, 图片查看器/image viewer→ui-image-viewer, 底部弹出/bottom sheet→ui-popup. Without the English aliases, an English-only or mixed query can silently miss an enrolled component even though its Chinese alias works.

Use common short terms and synonyms for each enrolled category, not just one phrasing per example, and cover the languages agents actually use. ### Large-repository type scope

Default to `typeScope: "project"` for small/medium projects: it keeps full dependency and inherited Prop types. For a large monorepo whose components import a server/lib/trpc/Prisma graph, set `typeScope: "componentRoots"`: only the component-root type graph is loaded, and imports outside the roots become shallow any-types. This keeps generation under the default Node heap.

Decide before the first generate. If generation OOMs, approaches 2 GB, or its TypeScript program includes server packages, switch to `componentRoots`; do not raise the heap as the fix, add `@ts-nocheck`, create manual stub files, or rewrite imports. Regenerate, then audit and check under the default heap. `generate`, `audit` and `check` expose `typeScope`, `typeCheck`, `suppressedTypeDiagnostics` and optional `suppressedTypeCodes`. Suppression is limited to semantic diagnostics in source files that imported a root-external stub; syntax errors, unresolved imports and untainted files still fail. `typeCheck: "partial"` is still not a full type-check pass. Report the tradeoff: local Props remain typed, but Props inherited from modules outside the roots may be `any`/partial. If those inherited types are essential, add the shared primitive package to `componentRoots` rather than claiming full type fidelity. More specific phrases take precedence over contained vocabulary terms; unrelated matched concepts still combine. For mixed-intent requests, prefer search `--per-layer 3`; it returns top-N per layer and overrides `--limit`, so a tail layer or its sixth item is not silently cut off. On a single-layer catalog, `--per-layer 3` automatically expands to 5; use `--per-layer 5` explicitly only when a multi-layer catalog has more than three strong candidates in one layer. Use `--layer auto` only for single-intent queries; it locks onto the top-ranked item layer and can hide a second requested role. Give complete task entrypoints and structural children distinct primary task tags when their roles differ, mapping ordinary selection queries to the complete control and related tags to its parts. Otherwise many equally tagged children can crowd the intended entry out of the bounded results. Do not change lifecycle status or IDs to manipulate ranking. Validate common and specific queries before handoff.

Existing relative imports are sufficient evidence to choose importPrefix: null without asking for a new alias. If ownership or a public package contract cannot be inferred, ask that specific missing question while continuing independent work. A directory name alone does not establish a public import contract. Relative entries save importPath: null; get --from takes a projectRoot-relative caller file and returns its derived specifier without reading sources. Verify at least one real caller during setup.

Each root can also declare `reuse: { scope: "project" }` or `reuse: { scope: "module", owner: "billing" }`. `owner` is a lowercase module identifier from project conventions (letters/digits separated by dots, underscores or hyphens); it is required for module scope and optional for project scope. Missing reuse becomes `unspecified`, never an assumption of project-wide access. `enrollment: public` requires catalog decisions but does not make a component globally reusable; `layer` alone is not an access policy. Review architecture and existing imports before setting a boundary, and preserve existing decisions unless the task authorizes a change.

Recommend reusable business controls as well as shared UI. A module-owned selector may be cataloged with module scope even if other modules must not import it. Keep page-private widgets/routes out by default. Entries inherit their root's reuse policy, including namespaces. Prefer disjoint roots aligned with existing directories when boundaries differ; do not move runtime code for this tool. In a genuinely mixed directory, an enrolled declaration may override the root with one `@catalogReuse project`, `@catalogReuse unspecified` or `@catalogReuse module:<owner>` tag. Derive this from actual ownership and imports, not convenience. Constraints still describe component-specific obligations; no automatic caller-module detection or import enforcement is provided.

## Annotate selected components

### JavaScript and mixed projects

The config field `tsconfig` can point to the project's `jsconfig.json`. Generation of JS/JSX requires effective `allowJs: true` (implicit for jsconfig); scan needs no compiler config. If the app deliberately excludes JS from its TypeScript checks, use a catalog-specific compiler config extending its existing configuration with allowJs enabled, rather than changing the application's policy. For a JS project without a compiler config, create one for the catalog using the actual JSX mode and module resolution during authorized setup. Do not migrate source files to TS for this tool. The CLI always analyzes with noEmit and never writes compiler outputs.

Read existing JSDoc `@param`, `@typedef`, `@type` and imported types. Untyped Props remain any/unknown or expose only inferred properties; preserve that uncertainty instead of inventing a type contract. Destructuring defaults are extracted, but runtime propTypes/defaultProps are not a substitute for a complete static API. Preserve checkJs and strictness choices; catalog checks under checkJs: false do not establish full JavaScript type safety. Use the consumer's lint/tests for runtime behavior. Metadata and actual example requirements are the same across JS/JSX and TS/TSX.

Static ESM/import() dependencies and ambiguous star exports are checked even with checkJs disabled. Bundler-provided modules need the project's corresponding type declarations/configuration. CommonJS exports currently report UNSUPPORTED_COMMONJS rather than passing as an empty scope; inspect their source and report the coverage gap without converting runtime module syntax or excluding reusable components just to pass.

### Component metadata

The Agent performs the metadata edits. Preserve existing JSDoc and runtime code. For each selected supported entry, inspect its declaration and actual uses, then add or complete:

```ts
/**
 * A factual summary of what this public component does.
 * @componentCatalog
 * @catalogStatus experimental
 * @catalogTask actual-task-tag
 * @catalogConstraint A real caller obligation established by the source or project contract.
 * @catalogExample preview src/previews/example.tsx | A real, relevant use
 */
```

This is a shape example, not text to paste verbatim. Every entry needs summary, marker, one status and at least one task, constraint and example. The first task is primary. An optional single `@catalogReuse project|unspecified|module:<owner>` overrides the root's boundary when actual ownership differs. Preserve established lifecycle decisions; otherwise use experimental. Passing extraction, having a production consumer or originating in a popular UI library is not alone evidence of project-level stability. Stable needs an established project/user maturity decision and a production/preview example; the CLI can verify only the latter. Deprecated needs @catalogDeprecatedReason or a real @catalogReplacement; no-successor retirement uses a truthful reason. Existing replacement-only metadata remains supported. The reason is only valid with deprecated status.

Examples are projectRoot-relative JS/JSX/TS/TSX paths and must really reference the export as a value. JavaScript examples need allowJs even when the component itself is TypeScript. Classify production/preview/test/story according to config and filename conventions. Prefer existing consumers or tests. If no example exists, add an appropriate local test/preview only when it fits authorized setup and existing conventions; do not create a production route for metadata. No current consumers means missing usage evidence, not internal ownership: exported reusable primitives and compound helpers may still be public. Never use internal, unsupported, exclusions or a narrower root merely to hide a missing example. If evidence cannot be completed within scope, leave the candidate pending and report the resulting audit failure; do not claim setup complete. Similarly, missing meaningful constraints are pending evidence, not permission to insert filler.

Preserve valid existing example references. Select examples per component; do not replace them all with one synthetic showcase merely to satisfy bindings. For compound controls, inspect what the wrapper already renders and follow an existing working composition: a content wrapper may own its portal or overlay. A valid import and a passing typecheck do not prove a preview works. If adding a preview, verify the affected interaction with the project's available browser/story/test workflow, or disclose that runtime behavior remains unverified.

Same-name local export lists (`const Button = ...; export { Button }`) and separate named default exports (`function Button() {...}; export default Button`) are supported; put annotations on the declaration, not the bare export statement. Default-only entries retain their declaration name as ID/exportName and report exportKind: default; if the declaration also has a same-name named export, the catalog prefers that named API.

Direct React imports support forwardRef/memo with inline callbacks or references to same-file functions/const renders, including memo around forwardRef, nested memo, import aliases and memo comparators. Named wrapped defaults such as `export default memo(Button)` and `export default memo(function Button() {...})` are supported: put metadata on that default export statement, since it exposes a different value from the private render. The ID uses the referenced declaration or named inline function. Preserve result assertions such as `memo(Button) as typeof Button` and satisfies expressions. Props and generics come from the public callable; destructuring defaults come from the resolved render. Keep wrappers, comparisons and assertions intact. Imported render references, arbitrary HOC compositions, third-party component aliases, anonymous defaults and alias-only local exports still need tool support; use source discovery rather than rewriting runtime code to fit the catalog.

Do not mark a known unsupported declaration. Record a truthful @componentCatalogIgnore unsupported: reason on an unmarked declaration and report the limitation; do not rewrite runtime behavior to pass. For private helpers or non-component PascalCase constants, use internal: reason or non-component: reason. The marker and ignore tag are mutually exclusive. Already marked unsupported declarations fail generation: fix only within authorized scope, without silently deleting existing metadata. See [maintenance.md](maintenance.md) for the decision contract. supportedShape=true and an empty missingMetadata list do not prove valid types, tags or example bindings.

Use audit for full configured coverage after scan's heuristic discovery. Resolved aliases and export-star barrels do not need duplicate annotations; annotate the original supported declaration. Unresolved, ambiguous or out-of-scope value reexports require investigation. Type-only exports are not components. A genuine external reexport can carry an explicit ignore reason at its export statement. Unsupported source formats and skipped symlinks are coverage findings, not proof of an empty component scope.

Verify one representative entry first when it helps catch configuration errors, then continue through the full selected scope. Preserve private components and user edits. Keep a temporary reasoning tally or final report, not a second persistent registry.

## Verify and hand off

Run audit and resolve enrollment/metadata findings, then generate, representative task/name/Prop searches, get, a focused --prop where useful, and check. Also query from another cwd with explicit --config to catch path assumptions. Confirm expected source/import paths, generic type context, output omissions and that queries do not modify the catalog. Run applicable project checks for annotations or added examples; report what actually ran. When integration is in scope, add generate/check scripts and a short project instructions pointer using [maintenance.md](maintenance.md). check covers missing enrollment as well as freshness; v1 generate --check alone cannot catch unmarked additions.

For full setup, verify three separate outcomes: the CLI/config can run, the selected scope is useful for discovery, and future changes reach the catalog check through the project's routine check command. A copied skill plus generated JSON does not establish the last outcome. Provide a persistent CLI entry that will work in the intended environment; a machine-specific absolute tool path is acceptable for explicitly local use but is not portable team setup. Preserve existing scripts and use the project's instruction-file convention for the short pointer. If the user requested only inventory or a local trial, report integration as not configured rather than expanding that task.

Verify integration from the final files, not from commands run earlier: execute the delivered query and check entrypoints, trace the routine check command to catalog check, and read back the project instructions pointer. Preserve these on upgrades. Report readiness, discovery and workflow integration separately when any remains incomplete; doctor and a direct CLI check cannot establish that routine checks are wired correctly.

Before querying, choose up to ten representative selection tasks from the reviewed scope, covering its distinct enrolled categories and the user's language, plus at least one mixed-role and one missing/edge case. Start with `verify --suggest` for export-name and unique-task smoke queries, then add mixed-role and missing/edge cases in the same queries JSON and run `verify --queries <file>`; `expectedIds` must appear in the top five, `absentIds` must stay absent. Use export-name queries to distinguish vocabulary gaps from missing enrollment. Fix missing task mappings and rerun the same task list without hiding failures. Report the hit count and unresolved tasks in conversation, not a new persistent report. Compare the reviewed directory coverage with the user's chosen scope: a UI-only catalog does not complete a request to include reusable business components. `discovery.status=partial` means unsupported exclusions remain even if status=pass; available does not prove usefulness. Report limitations and source-search fallbacks honestly.

On failure, use the concrete path and next action in the error. No markers with undecided candidates means review and annotate, not endlessly retry generate. v2 allows zero entries only if auditing has no unresolved candidates; ignored entries remain visible in counts. Missing catalog means explicit generation; an empty search may mean missing vocabulary or an unindexed inherited Prop. Search names/tags and inspect source before concluding the component does not exist.

Finish in the user's language with the selected directories and a compact coverage report: discovered candidates, selected candidates, generated entries, skipped items/reasons and pending evidence. Reexports can refer to the same underlying component; do not present raw candidate counts as unique components. Provide working commands that include the actual script/bin and config path, plus the regeneration/check command. If only a subset is ready, say exactly which subset is usable. Do not claim completion merely because generate passed.
